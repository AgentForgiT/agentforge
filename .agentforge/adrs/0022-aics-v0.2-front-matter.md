# ADR-0022: AICS v0.2 Structured Front Matter

Metadata:

- Status: Accepted
- Date: 2026-08-01
- Deciders: AgentForge maintainers
- Issues: #115, #116, #117, #118, #119
- Related: `.agentforge/specs/aics-v0.1.md`, `aics-validation-v0.1.md`

## Context

AICS v0.1 (Genesis Sprint 3) defined portable project context with plain-Markdown `Metadata:` blocks and explicitly deferred structured front matter: "A future version may define structured front matter." It also defined three adoption levels without validator support — `validate-context` returns a flat error list.

AICS is the project's moat: the standard that makes project context machine-parseable and tool-portable. Without structured metadata, tools must regex-scan prose; without level reporting, projects cannot demonstrate progression. v0.2 closes both gaps while remaining backward-compatible.

## Decision

Adopt **YAML front matter as the recommended structured metadata format** for AICS v0.2:

- A document carries front matter when its first line is `---`, a YAML block follows, and a closing `---` line terminates it before body content.
- Required fields: `status` (draft/active/superseded/accepted as appropriate) and `aics-version: 0.2`.
- Recommended fields (from the v0.1 metadata list): `version`, `phase`, `applies-to`, `related-issues`, `related-adrs`, `last-updated`.
- **Backward compatibility**: plain `Metadata:` blocks (v0.1 style) remain accepted. A document passes metadata checks if it has either front matter or a `Metadata:` block. Front matter is required only for Level 3 declaration.

Adoption levels become machine-reported:

- **Level 1, Context Present**: required directories and files exist.
- **Level 2, Context Governed**: metadata (either style) present in the metadata-checked files; templates and required-text checks pass.
- **Level 3, Context Validated**: front matter with `aics-version` present in the metadata-checked files, `.agentforge/aics-version` marker exists, all checks pass, and validation runs in CI.

A `.agentforge/aics-version` file (content `0.2`) declares the context's spec version. Absence means v0.1 context: Level 2 maximum, with a warning when the project declares Level 3 intent.

Warnings (recommended files missing, plain-Metadata style at Level 3) never fail validation — they inform.

## Consequences

- Context becomes machine-parseable: tools can extract `status`, `version`, and linkage without scanning prose.
- Existing v0.1 projects keep validating; only Level 3 declaration requires migration.
- AgentForge dogfoods: its own context migrates to front matter and reports Level 3 — the spec is its own first adopter.
- The CLI (`validate-context`) and the WASM in-browser validator both surface level + warnings.
- The validator stays offline and dependency-free: front matter is parsed with string checks (no YAML library), keeping the 80-line stdlib ethos.

## Alternatives Considered

- **Require front matter for all contexts** — rejected: breaks every existing v0.1 project and the incremental-adoption goal.
- **TOML/JSON metadata** — rejected: YAML front matter is the de-facto standard in Markdown tooling (Jekyll, Hugo, Obsidian) and the most tool-portable.
- **External schema file (JSON Schema)** — deferred: overkill for the current rule set; may come with AICS v0.3 tooling.
- **Keep plain metadata forever** — rejected: leaves the v0.1 promise unfulfilled and the moat weaker.

## Deferred

- JSON Schema for front matter.
- Automatic migration tooling for v0.1 → v0.2 contexts.
- Per-file `aics-version` granularity (v0.2 uses a single version marker).
